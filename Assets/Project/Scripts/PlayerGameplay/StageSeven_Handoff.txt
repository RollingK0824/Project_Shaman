2. Ghost 인터페이스 계약 — 폐기 없음
----------------------------------
파일: PG/Health/IDamageable.cs
API: bool IsDead { get; }; void ReceiveDamage(float amount, GameObject source = null)
값: HP 피해량, 공격 주체(source). 공격 시스템은 양의 유한값만 요청한다.
호출자/시점: 서버의 단일 피해 판정자가 승인한 뒤 한 번 전달.
실패: void이므로 승인/실제 HP 감소 응답이 아니다. 수신자에서 무적/사망 등을 거절한다.
수신자는 자기 HP/사망 API를 호출한다. 다른 대상 HP를 직접 쓰지 않는다.

파일: PG/Items/Combat/IItemControlReceiver.cs
API: bool TryApplyItemControl(ItemControlEffect effect, GameObject source)
effect.Kind: Slow / Stagger / SensoryInterference.
effect.Duration: 초 단위, 양의 유한값.
Slow: SpeedMultiplier > 0, <= 1 (0.6이면 기본 속도의 60%).
Stagger: Duration 동안 행동/이동 억제 요청. 구체 AI state는 수신자 결정.
SensoryInterference: Senses = Vision(1) | Hearing(2), None은 유효 요청 아님.
반환 true: 수신자가 요청을 수락했다. false: 면역/상태/중첩 정책 등으로 거절했다.
누가/언제: 승인된 ItemAttackSession.TryHit가 실제 Collider 접촉 시 호출.
실패 시: 같은 공격에서 다른 Collider로 재시도하거나 legacy로 우회하지 않는다.
Duration 만료, 중첩/갱신/최강 효과 선택, 사망/풀 재사용 초기화는 수신자 책임.
공격 볼륨 lifetime과 CC Duration은 서로 다르다. 볼륨이 사라져도 수락한 CC는 유지한다.
ItemControlEffect만으로 AI를 정지/감속시키지는 않는다.

파일: PG/Items/SaltItem/ISaltReactable.cs
API: bool ReactToSalt(GameObject user)
HP 계약이 없는 기존 소금 반응 대상 호환용. true는 반응 수락, false는 거절.
피해량/기간을 받지 않는다. 신규 HP 피해는 IDamageable이 우선.

파일: PG/Items/BeanMugwort/IBeanMugwortReactable.cs
API: bool ReactToBeanMugwort(GameObject user, float slowMultiplier, float duration)
기존 타래 반응 대상 호환용. 배율/초 전달, true 수락/false 거절.
수신자가 둔화 중첩과 만료/복원을 책임진다.

파일: PG/Items/BellItem/IBellReactable.cs
API: void ReactToBell(GameObject user)
기존 방울 반응 호환용. 기간/경직 강도나 거절 응답은 없다.
신규 경직은 IItemControlReceiver가 Duration을 받는다.
ICoinReactable 등 별도 관찰/반응 인터페이스도 이번 단계에서 폐기하지 않는다.

[중복 정책 — 반드시 읽을 것]
PG/Items/Combat/ItemAttackSession.cs는 공격마다 새 객체를 만든다.
초기 Overlap과 OnTriggerEnter가 같은 session을 공유한다.
Collider.GetComponentInParent로 수신자를 찾고 수신 Component의 GameObject를 키로 기록한다.
한 배우의 모든 Collider가 같은 부모의 HP/CC 수신자를 찾도록 배치한다.
히트박스마다 별도 수신자를 두면 다른 배우로 인식할 수 있다.
HP/CC/legacy 수신 컴포넌트는 같은 배우 root에 모으는 구성을 권장한다.
호출 전에 기록하므로 재진입/재접촉/거절된 면역 대상도 한 공격당 시도는 한 번이다.
새 공격은 새 기록. 다른 공격자의 공격까지 전역 차단하는 정책은 없다.
해당 공격에 공통 HP 또는 CC 계약이 있으면 legacy는 추가 호출하지 않는다.
공통 CC 거절 시에도 legacy fallback은 호출하지 않는다.
죽은 대상/공격자, 권한 상실, 자기 Collider, 마스크 밖/비활성 Collider는 차단한다.
PG/Health/DamageTrigger.cs의 일반 환경 피해 oncePerEntry는 별개로 마지막 Collider가
나갔다 다시 들어오면 재피해 가능하다. 아이템 session은 Exit로 기록이 초기화되지 않는다.

[피해 요청과 실제 피해 구별]
DamageSource.RequestDamage → PlayerEvents.DamageRequested는 프로세스 내부 이벤트다.
RequestDamage 반환 true / ItemAttackSession.HitApplied / AppliedTargetCount는
유효 피해 요청 발행 또는 CC/legacy 수락이며 실제 HP 감소 ACK가 아니다.
NET/Player/NetPlayerHealth는 자신의 PlayerHealth 요청만 받는다.
Ghost 담당 서버 수신기가 Ghost 대상 요청을 한 번만 ReceiveDamage로 전달해야 한다.
온라인에서 LocalGameplayJudge를 켜거나 NetPlayerHealth와 중복 전달하지 않는다.
소금 성공/소모 콜백은 이 요청 결과를 사용하므로 서버 판정/수신 경로를 연결하기 전
공격 gate를 무조건 true로 열지 않는다. 면역에서 소비할지 여부도 팀 규칙으로 확정한다.

3. Network 요청 → 검증 → 확정 계약
----------------------------------
공통: 이 문서의 이벤트는 C# 로컬 이벤트이며 자동 네트워크 메시지가 아니다.
Expected Caller는 인증된 연결의 실제 소유 Player를 찾은 Network 서버 어댑터다.
클라이언트가 보낸 GameObject/ScriptableObject를 그대로 신뢰하거나 전송하지 않는다.
registered item ID, world netId, recipe key, instance ID를 서버 레지스트리에서 해석한다.
재전송 request ID/nonce, 중복 승인 방지, 라운드/거리/소유권/사용 간격 검사는 어댑터 책임.
구독/해제는 해당 Player 생명주기에 맞춘다. static 이벤트는 interactor/target을 필터링한다.

요청: PickupRequested(GameObject interactor, WorldItem item)
흐름: F → PlayerInteractor → WorldItem.Interact → event → Network 검증.
확정: inventory.TryAddItem(item.ItemData, amount=1) == true인 뒤에만 월드 제거.
재료면 사전 inventory.BindSharedMaterials(서버 세션 store) 및 store gate 연결 필수.
실패: 월드 유지, 수량 유지, 요청자에게 거절 통지. 다른 플레이어의 선점은 서버에서 직렬화.
WorldItem.ApplyCollected()는 오프라인 숨김/수거 상태 API다. 온라인 despawn 대체가 아니다.
현재 NET/Player/NetPlayerInventory.CmdRequestPickup은
  CanAct/IsDead/GameManager/CanInteract/거리4.5/DB ID를 검사하지만,
  world despawn/destroy 후 TryAddItem 결과를 무시하고 SyncList에 추가한다.
  팀원 수정 필요: grant 성공 전 파괴 금지, 같은 world 중복 요청 직렬 처리.
이번 작업에서 해당 코드나 월드 NetworkIdentity는 수정하지 않았다.

[Craft]
파일: PG/Inventory/PlayerCraftingController.cs, CraftingRecipeData.cs
요청: RequestCraft(recipe) → CraftRequested(CraftingRecipeData recipe)
반환: RequestCraft의 true는 온라인에서는 요청 발행 가능/발행을 뜻하며 제작 완료 아님.
UI 미리보기: CanCraft/CanRequestCraft. 서버에서도 다시 검증해야 한다.
확정: SetAuthorityCheck(Func<bool>) 연결 후 서버 TryCraft(trustedRecipe).
  SharedMaterialInventory에도 서버 gate, recipient에는 동일 세션 store binding 필요.
  true일 때 재료 지출+개인 결과물이 원자적으로 확정되고 Crafted(recipe) 발생.
실패: false면 재료/결과 변화 없음. 승인 전에 TryCraft/TryExchange/TryRemove 호출 금지.
현재 recipe에는 고유 wire ID가 없다. 어댑터는 서버의 고정 catalog key를 정해야 한다.
recipe key만 요청 받고 비용/결과/수량은 서버 RecipeData에서 읽는다.
Shared TryExchange와 개인 TryExchange를 추가로 각각 호출하면 이중 제작이므로 금지.
현재 Network 폴더에서 CraftRequested 구독/제작 전송 연결은 발견되지 않았다.

[공용 재료]
파일: PG/Inventory/SharedMaterialInventory.cs
서버 API: SetAuthorityCheck(Func<bool>), TryAdd(requester,item,amount),
  TryRemove(requester,item,amount), TryExchange(recipient,costs,result,amount), ResetSession().
검사: Material만, 양의 수량/overflow/소유자 생존/권한/재진입 검사.
권한: 순수 클라이언트는 delegate=true라도 변경 불가. 서버는 delegate 없으면 차단.
서버 성공 후: Changed / MaterialCountChanged로 네트워크 publish를 예약한다.
Export: Dictionary<ItemData,int> ExportSnapshot(out long version) — 전체 복사, 메인 스레드.
  외부에서 복사본을 바꿔도 원본 수량/버전이 바뀌지 않는다. 호출만으로 버전 증가 없음.
  DTO로 바꿀 때 ItemData를 등록된 ID로 치환. Counts는 라이브 상태 조회용이다.
클라이언트: bool ApplyReplicatedSnapshot(long version, IReadOnlyDictionary<ItemData,int> snapshot)
  순수 client에서만 허용, version > 현재 Version, 전체 교체. delta 아님.
  null/잘못된 종류/음수 수량은 전체 거절, 0은 제거. false면 부분 반영 없음.
버전: 성공한 변경마다 증가, ResetSession도 증가(0으로 리셋하지 않음).
  초기 양쪽 Version=0인 빈 상태는 이미 같으므로 v0을 억지로 apply하지 않는다.
  초기 강제 전송이 필요하면 서버 ResetSession 후 v1 전체 상태를 전송한다.
  재접속/새 세션은 새 replica 또는 담당자가 관리하는 세션 epoch로 분리한다.
  늦은/중복 패킷은 무시, invalid ID/수량은 재동기화 요청. Host에 apply하지 않는다.
개인 결과물과 공용 재료 snapshot은 동일 서버 제작 트랜잭션 결과로 묶어 보내야 한다.

[개인 소지품과 기존 네트워크 한계]
PG/Items/PlayerInventory.cs Items/GetItemCount, ItemUnitsChanged/ItemCountChanged/
InventoryChanged는 조회/변경 알림이다. 개인용 versioned Export/Apply API는 현재 없다.
TryAddItem/RemoveItem/ConsumeItem은 확정 변경이며 요청 API가 아니다.
개인 일반 아이템 경로 자체에 공용 store와 같은 Network authority gate는 없다.
따라서 어댑터가 서버 승인 후에만 mutation을 호출해야 한다.
현재 NetPlayerInventory는 SyncList<int> OnAdd만 반영하며 제거/소진/초기 전체 목록
복원, 제작 결과, 공용 재료, 그림 인스턴스 상태를 모두 다루는 구현이 아니다.
아이템별 ID 추가만으로 인벤토리 동기화가 끝나지 않는다.
개인 full-state/델타 프로토콜과 재접속은 Network 담당 후속 합의 사항.
현재 확정 API를 재사용할 수 있으나 죽은 player/영구 notebook/그림 instance의
수량을 무작정 RemoveItem/TryAddItem으로 맞추는 snapshot 루프를 만들지 않는다.
이 단계에서는 별도의 개인 네트워크 인벤토리를 새로 만들지 않았다.

[일반 아이템 Use]
파일: PG/Input/PlayerInputReader.cs, PG/Items/PlayerItemController.cs,
      PG/Items/ItemBase.cs, PG/Items/Combat/ItemAttackAuthority.cs
기존 요청 입구: PlayerInputReader.UseItemStarted / UseItemCanceled (인자 없음).
  로컬 adapter는 EquippedItemData/EquippedTalismanInstanceId로 intent를 구성한다.
  입력 이벤트는 성공 통지가 아니며 Notebook/관찰 UI 같은 로컬 동작도 구별해야 한다.
ItemBase.Initialize(trustedData, serverOwner), OnUseStarted()/OnUseCanceled()는
  서버가 승인한 아이템 동작 호출점이다. void 반환은 사용 성공 ACK가 아니다.
  서버 어댑터가 trusted gameplay 인스턴스/조준 근거를 준비해야 한다.
  로컬 PlayerItemController의 private 입력 함수를 reflection으로 호출하지 않는다.
공통 공격 권한: ItemAttackAuthority.SetAuthorityCheck(Func<bool> canResolve).
  온라인은 NetworkServer.active + enabled gate + delegate=true만 허용.
  소유/쿨다운/소모 승인 후 gate를 유지. 접촉마다 delegate가 평가되므로
  delegate 안에서 다시 소비하거나 쿨다운을 시작하지 않는다.
  권한 철회/사망 시 비행 중인 타래와 지속 볼륨도 차단된다.
실제 성공 통지는 기존 PlayerItemActions.ReportUse 경로를 사용한다.
  요청/예측 VFX 시점에 퀘스트 Use를 다시 보고하지 않는다.
NET의 Equipment는 시각 장착 동기화이며 공격 Use 승인 연결이 아니다.
현재 일반 아이템 전용 UseRequested DTO 이벤트를 중복 추가하지 않았다.
서버 gameplay instance/aim/투척 spawn/VFX 복제와 input 연결은 Network 담당 후속.

4. 효과 부적 — 저장 / 사용 / 복제
--------------------------------
파일: PG/Items/Talisman/PlayerTalismanCollection.cs
저장 요청: RequestSave(item,draft,name,effectId) → SaveRequested(item,TalismanSaveData).
  온라인 pending은 false 반환, 빈 부적 소비/그림 확정 없이 기다린다.
서버 확정: collection.SetAuthorityCheck; SaveFinal(trustedItem,payload).
  서버가 template/blank 소유, 이름/그림/effect 허용, 요청 중복을 검사한다.
  true면 blank -1 + 고유 그림 +1 원자적 처리, DrawingSaved/SelectionChanged.
  false면 소비 없음. UI를 성공으로 닫지 말고 사유 전달.
TalismanSaveData payload 최소값:
  InstanceId, CustomName, EffectId, DrawingJson(= DrawingData의 최종 직렬화).
  실시간 stroke/RenderTexture/prefab/ScriptableObject 전송은 필요 없다.
  최대 이름 12자, instance ID 64자, JSON 600000자, 512 strokes/8192 points.
  좌표 [0,1] 내 유한값, 실제 잉크 유효성, JSON ID와 외부 InstanceId 일치 검사.
  이미 저장된 ID replay는 재소비하지 않는다. 악성 고유 ID 반복/전송율/용량은
  서버 어댑터에서 추가 제한한다. 클라이언트가 보낸 ID는 인증 소유권 증거가 아니다.

사용 요청: collection.RequestUse(instanceId) → UseRequested(string instanceId).
  온라인 pending은 false, local 효과/소비 없음.
확정: collection.TryUse(instanceId), effects.SetAuthorityCheck도 별도 연결.
  실제 소유 그림에서 EffectId → 서버 TalismanItemData.FindEffect로 해석한다.
  성공 시 효과 적용, ConsumeOnUse 정책대로 instance 소비, 성공 이벤트.
  실패 시 효과/소비 없이 거절. 서버가 현재 장착 instance와 요청 일치를 검증한다.
클라이언트에서 신뢰하면 안 되는 값: Effect Magnitude, Duration, ConsumeOnUse,
  stack 정책, HP/Stress 결과. 모두 서버 EffectDefinition에서 결정한다.

소유 그림 export: collection.Export(template) → TalismanSaveData[].
소유 그림 apply: ApplyReplicatedSnapshot(version,template,records).
  순수 client만, version 증가 필수, 최대512개, 중복ID/invalid효과/그림 전체 거절.
  해당 template의 전체 목록 교체. 빠진 ID는 없어진 것으로 처리되어 슬롯 정리.
  collection의 version은 template별이 아니라 collection 전체 기준이다.
  현재 canonical 효과 부적 한 template 기준. 여러 template 패킷에 같은 version을
  붙여 연속 apply하지 않는다. 확장 시 담당자가 batch/순서를 합의해야 한다.

활성 효과 export: PG/Items/Talisman/PlayerTalismanEffectController.cs ExportState().
  TalismanEffectState[] = EffectId + RemainingDuration(초).
apply: ApplyReplicatedState(version,states,Func<string,TalismanEffectDefinition> resolve).
  순수 client만, alive/enabled, 증가 version, <=32개, 중복 effect ID 거절,
  양의 유한 RemainingDuration <= trusted definition.Duration. 모두 검증 후 교체.
  magnitude/consume는 payload에서 읽지 않고 local trusted catalog로 해석한다.
  서버가 보낸 RemainingDuration만 수락. 네트워크 지연 보정/서버시각은 adapter 책임.
  0초 만료 항목은 제외하고 전체 상태를 보낸다.
  ResetEffects는 snapshot version을 리셋하지 않는다. 같은 replica에서는 round를
  넘어 버전을 단조 증가시키고, 다른 세션 패킷을 섞지 않는다.
  collection.ResetRound는 그림/중복 저장 기록을 지우므로 지연 Save replay도
  새 round에 통과하지 않게 adapter가 세션/round ID를 검사해야 한다.

장착 값: PlayerItemController.EquippedItemData + EquippedTalismanInstanceId.
  inventory.GetQuickSlotInstanceId(index), AssignTalismanQuickSlot(index,id)로 로컬 선택.
  NetPlayerEquipment는 현재 template ItemData/int ID만 비교한다.
  같은 종류의 서로 다른 그림으로 교체는 감지하지 못하며 instance 소유도 검증 못함.
  기존 _inventory.Contains(template)만으로 저장된 그림 소유를 판정하지 말 것.
  collection.Find(instanceId,out template)로 소유를 확인하고 장착 instance ID를
  별도로 복제해야 한다. ApplyRemoteHeldVisual(ItemData)는 현재 template 표시 API다.
  원격 그림 표면까지 표시하는 binding은 Network/표현 담당 후속 연결이다.

5. Health / Stress / Death 연결 표
---------------------------------
Health 요청 파일: PG/Event/PlayerEvents.cs + Health/DamageSource.cs.
  DamageRequested(target,amount,source) → 현재 NET/Player/NetPlayerHealth.HandleDamageRequested.
  현 adapter는 target==자기health, 생존/수치/게임상태 검사 후 ApplyHealth(next,source),
  0이면 ApplyDeath(source). 이 경로에 ReceiveDamage를 추가로 호출하면 이중 피해다.
대안 단일 확정 API: PG/Health/PlayerHealth.ReceiveDamage(amount,source).
  서버 승인 후 한 번 호출, SetAuthorityCheck로 권한 제한. 내부 사망 흐름 포함.
  bool 응답 없음. DamageRequested 라우팅 또는 직접 ReceiveDamage 중 한 경로만 사용.
Health 복제: 기존 NetPlayerHealth HP hook → ApplyHealth(current,source=null).
  절대 HP 설정, 피해 차이만 Damaged 발행. ApplyHealth(0)만으로 사망 통지하지 않는다.

Stress 요청: PG/Stress/PlayerStressController.UseExternalAuthority=true;
  ReceiveStress(amount,cause,source) / zone rate → PlayerEvents.StressRequested(target,delta,cause,source).
  NET/Player/NetPlayerStress의 handler는 target/수치/생존/GameManager/시작 gate 검사 후
  SetStress(CurrentStress+delta). 이 이벤트 자체는 클라이언트→서버 전송이 아니다.
  서버에서 노출/안전지역을 판정하거나 Network 담당이 원인을 검증하여 서버 요청 생성.
  클라이언트가 임의 delta를 보냈다고 신뢰하지 않는다.
Stress 확정/복제: SetStress(float absolute), 유한값/0~100 clamp, 이벤트로 HUD 갱신.
  요청 delta에는 부적 배율이 이미 적용될 수 있다. snapshot에는 다시 배율 적용 금지.
  순수 client HP처럼 stress 절대값 적용, 원격 단계 표시는 ApplyStressLevel(enum).
  AddStress/ReduceStress/SetStress 자체는 요청/인증 API가 아니므로 승인 전 사용 금지.

지속 Stress → HP: PG/Stress/PlayerStressDamage.SetServerAuthorityCheck(Func<bool>).
  온라인에서 서버 + 명시 gate 없으면 tick 차단. Update가 Advance를 호출하므로
  어댑터가 별도로 Advance를 매 프레임 중복 호출하지 않는다.
  threshold/hold/tick은 서버 Inspector 신뢰값. source는 자식 StressDamage.
  실제 피해는 PlayerHealth.ReceiveDamage → HealthChanged/Died, 기존 NetHealth가 관찰.
  HP를 직접 빼거나 다른 tick timer를 새로 만들지 않는다.

Death 서버: health.ApplyDeath(source) → gameplay shutdown → PlayerDeathVisual → Died →
  DeathConfirmed. 기존 NetPlayerStatus.HandleDeathConfirmed가 자기 player만 동기화.
Death client: 기존 NetPlayerStatus hook/OnStartClient → health.ApplyReplicatedDeath(source).
  internal API(현재 Project.Runtime assembly 내부에서 기존 adapter가 접근).
  사망 중복 처리 방지, Root/NetworkIdentity 유지, 이동/사용/상호작용 중단,
  HeldVisual 제거, 캐릭터 표현 처리 후 Died로 로컬 관전 전환.
  NetworkPlayer에 PlayerDeathVisual 구성/CharacterVisual 참조가 없는 문제는
  담당자가 프리팹에서 연결해야 한다. 이 단계에서는 추가하지 않았다.
  원격에도 death 상태 전달 필요, 관전 입력/카메라는 로컬에만 활성화.
실패/거절: dead/invalid/authority=false 피해는 무시. 사망 snapshot은 같은 플레이어에
  반복 적용해도 idempotent. 새 round 부활/새 player 수명은 담당자 프로토콜로 처리.

6. NetItemDatabase 등록 요청 (DB 수정하지 않음)
--------------------------------------------
파일: NET/Item/NetItemDataBase.cs
asset: Assets/Project/Data/Items/NetItemDatabase_Proto.asset
GetId(ItemData)=_items.IndexOf, GetItem(int)=범위 내 참조 또는 null, 미등록=-1.
정수 ID는 list 순서다. 기존 entry 삭제/삽입/재정렬 금지. 팀원이 append하고
Host/Client 동일 catalog revision을 배포해야 한다.

문자열 ItemData.ItemId는 quest TargetId/Reward.Id용이며 위 정수 ID와 별개.

7. 담당자 연결 순서 / 확인
------------------------
1) 실제 사용할 Network Player/씬/등록 catalog를 확정하고 최신 PlayerGameplay 구성 대조.
2) 세션 SharedMaterialInventory 하나 생성/소유, 플레이어 전원 BindSharedMaterials.
3) 서버 authority gates를 명시 연결하고 offline LocalGameplayJudge는 온라인에서 끔.
4) pickup은 grant 성공 → despawn 순서, 제작은 단일 TryCraft 후 관련 상태 publish.
5) Ghost root 공통 수신자/서버 damage router 한 곳, CC 타이머/중첩/이동/감각 연결.
6) 사용 intent/서버 gameplay instance/조준/소진/쿨다운과 전송 재시도 중복 방지.
7) 부적 save/use + 소유 목록/blank 수량/장착 instance/활성 효과 일관된 복제.
8) health/stress/death 및 늦은 접속·재접속·라운드 초기화 검증.
9) Host + 순수 Client 실제 플레이로 타깃 중복Collider/동시획득/동시제작/소진/
   부적 재전송/사망/접속 복원 검증. 이번 Dummy 성공을 실제 네트워크 성공으로 대체 금지.

검증 자료: StageSeven 결과 폴더의 handoff-checks.txt, 기존 408 회귀 결과,
unity-resolved-prefab-audit.txt, item-registration.csv, scope-audit.json, 테스트 보고서.
